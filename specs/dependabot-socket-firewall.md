# Dependabot Socket Firewall Workflow

## Objective

Every PR opened by Dependabot is re-installed through Socket Firewall Free (`sfw`) and closed automatically if the install fails, so a malicious or compromised dependency never sits mergeable in a repo that deploys to Railway on push to `main`.

## Context

`.github/dependabot.yml` covers `pip` for `/` and `/shared`, `docker` and `github-actions`, but nothing reviews what it proposes. Dependency management is Poetry, not raw pip: two independent projects (`pyproject.toml` + `poetry.lock` at the root and in `shared/`). The approach was validated in DataScience-Docker (spike, PR #38): `sfw poetry install` fails with `CERTIFICATE_VERIFY_FAILED`, so the lock is exported and installed with `sfw pip install -r`. This spec adapts it to this repo's two projects. The global spec and plan live in meta-projects (`specs/global/expand-dependabot-socket-firewall*.md`).

This repo is in meta-projects' `no_automerge_repos.txt`: the implementation PR needs human review and merge.

## Requirements

### Functional Requirements

- [x] `.github/workflows/dependabot-socket-firewall.yml` runs on `pull_request` to `main`, only when `github.actor == 'dependabot[bot]'`
- [x] Root project: `poetry export --without-hashes --with api,fetch,ml,dev` → `sfw pip install -r`
- [x] `shared/` project: same flow, run when the PR modifies files under `shared/`
- [x] The PR is closed with an explanatory comment when either install step fails
- [x] Actions pinned by commit SHA (same as the validated reference); job-level `permissions: pull-requests: write, contents: read`

### Non-Functional Requirements

- [x] Safety: only closes `dependabot[bot]` PRs; never merges; no new secrets (`github.token` only)
- [x] `GH_TOKEN` is exposed only to the steps that call `gh`, not to the install steps that run third-party build code
- [x] Reversible: deleting the workflow file removes the whole behavior

## Architecture

Single job `socket-check`: checkout → `setup-python` 3.13 → export locks → detect whether the PR touches `shared/` → `SocketDev/action` (`firewall-free`) → install root / install `shared/` (`continue-on-error`) → close PR if any install failed.

### Decisions

| Decision | Choice | Why |
|----------|--------|-----|
| Poetry version | 2.4.1 + `poetry-plugin-export` 1.10.1 (not 1.8.4) | `poetry.lock` is `lock-version 2.1`, generated by Poetry 2.4.1 (the version PR #91 aligns the Dockerfiles to). Verified in a `python:3.13-slim` container: 1.8.4 exports it but warns "The lock file might not be compatible"; 2.4.1 reads it cleanly and also reads `shared/poetry.lock` (generated by 1.8.4). |
| Python | 3.13 | Dockerfile base image and mypy target; satisfies `^3.12` so markers are honoured by pip |
| Groups | `--with api,fetch,ml,dev` | `api`/`fetch`/`ml` are `optional = true`, and export omits dev; without them most bumps would skip the firewall |
| Root vs `shared/` | Export both; install separately | Dependabot opens PRs for both directories. Root pins pytest `^8`, `shared/` `^7.4`: one combined `pip install -r a -r b` cannot resolve and would close every PR |
| When `shared/` runs | Only if the PR touches `shared/` | Keeps root PRs independent from `shared/` state (see risk below) |
| `-e file:///.../shared` line | Stripped from the root export | Local path dependency, not from a registry; its own dependencies are exported as regular pins |

## Testing Strategy

CI workflow YAML, no application code; the acceptance scenarios cannot be exercised without a real Dependabot PR (only `dependabot[bot]` triggers the job).

- Static: `actionlint` and YAML parse (both clean).
- Export: `poetry export` with the pinned versions in `python:3.13-slim` succeeds for the root lock; exported requirements contain `main` + `api`/`fetch`/`ml`/`dev` packages (fastapi, tensorflow-cpu, xgboost, pytest, ruff, mypy, cosmic-ray) and `pip install --dry-run -r` resolves them on Python 3.13.
- Acceptance (from the issue): blocked package → PR closed with comment; clean install → PR stays open; human PR → job skipped by the actor guard. Observed on the first real Dependabot PR after merge (Definition of Done).

## Boundaries & Constraints

### In Scope
- The workflow file and this spec.

### Out of Scope
- Regenerating `shared/poetry.lock` (see risks), changing `dependabot.yml`, the Socket Security GitHub App.

### Known risks
- **Closes on any install failure**, not only firewall blocks (network, PyPI outage, wheel that fails to build). `sfw` writes a JSON report with a `blocked` field that could distinguish them, but its schema was not validated against a real block. Accepted trade-off, same as the reference.
- **`shared/poetry.lock` is stale on `main`**: it lacks `alembic` and `mako`, added to `shared/pyproject.toml` later. Poetry 2.4.1 refuses to export it ("pyproject.toml changed significantly since poetry.lock was last generated"), so until `poetry lock` is run in `shared/`, Dependabot PRs touching `shared/` get a red job and are **not** checked (not closed). The export step fails loudly instead of checking a lock that silently omits packages.
